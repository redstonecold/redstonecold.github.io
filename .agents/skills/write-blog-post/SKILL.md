# 블로그 글 작성

## 적용 범위와 진행 방식

- 이 저장소의 새 글과 사용자가 수정 요청한 기존 글에 적용한다. 기존 글 전체나 사이트 공통 디자인을 일괄 변경하지 않는다.
- 주제와 자료를 받아 개요 승인 단계 없이 완성도 있는 전체 초안을 작성한다. 설명의 깊이, 논리 연결, 예제의 정확성과 시각 자료의 필요성을 초안 단계에서 검토한다.
- 사용자가 지정한 분량과 범위를 한 글로 작성한다. 분량이 없으면 필요한 기준을 질문한다. 범위와 분량이 충돌하면 작성 전에 충돌하는 부분만 짚어 조율한다. 임의로 내용을 축소하거나 여러 글로 나누지 않는다.
- 자료가 부족하면 부족한 내용을 특정하고 진행 방법을 사용자에게 묻는다. 임의로 추가 조사하거나 추측으로 채우지 않는다. 추가 조사가 허용되면 그 범위에서 수행한다.
- 사용자에게 필요한 질문은 한 번에 하나씩 한다. 이미 합의된 취향을 다시 묻지 않는다.
- 로컬 초안과 실제 블로그 미리보기를 제공한다. 사용자가 검토하고 승인한 뒤에만 커밋·푸시한다. 초안 작성 요청 자체를 게시 승인으로 간주하지 않는다.

## 독자와 문체

- 독자는 기초 지식이 있는 전공자다. 기초 개념의 반복 설명보다 핵심 원리, 이유, 논리의 연결과 헷갈리는 지점에 집중한다.
- 한국어로 작성하며 발표하듯 읽어도 자연스러운 평서체인 `~한다`, `~이다`를 사용한다. 문장은 명료하게 쓰되 전보식 단문으로 잘게 끊지 않는다.
- `알아보자`, `살펴보자` 같은 상투적 도입, `단순한 A가 아닌 B` 같은 과장된 대비, 근거 없는 `매우 중요한`, `강력한` 같은 수식어를 피한다. 구체적인 사실과 작동 원리를 바로 설명한다.
- 전문 용어는 첫 등장뿐 아니라 등장할 때마다 `영문(한글)`로 표기한다. 예: `gradient descent(경사 하강법)`. 실행 코드, 식별자, URL, 수학 기호 자체를 번역해 변형하지 않는다.

## 구성과 설명 깊이

- 해설형으로 작성한다. 요점과 비교는 적합한 그림·표로 정리하고, 문단은 이유와 논리를 설명한다. 그림·표의 내용을 본문에서 그대로 반복하지 않는다.
- 제목과 소제목은 `경사 하강법의 학습률`, `학습률과 수렴`처럼 간결한 개념형으로 짓는다. 전문 용어 표기 규칙은 제목에도 적용한다.
- 모든 글 상단에 목차를 표시한다. 본문 소제목에는 `1.`, `1.1.` 형태의 계층 번호를 사용하며 목차의 번호·문구·링크가 본문과 일치하게 한다.
- 개념 해설은 핵심 개념부터, 방법·기술 소개는 해결하려는 구체적인 문제부터 시작한다. 모든 글에 동일한 도입 형식을 강요하지 않는다.
- 기본은 직관 중심이다. 원리와 이유를 설명하고 수식은 이해에 필요한 만큼 포함한다. 수식 자체가 주제라면 수식의 의미와 근거를 중심으로 설명하되, 불필요한 유도와 반복 계산은 생략한다. 핵심 논리 단계까지 생략하지 않는다.
- 예시는 작은 숫자를 직접 계산하거나 실제 적용 상황을 보여주는 방식으로 든다. 계산 결과, 단위, 조건과 본문의 설명이 일치하는지 확인한다.
- 코드는 원리를 보여주는 짧은 핵심 부분만 포함한다. 설치 안내, 반복 설정, 보조 함수 등은 이해에 꼭 필요할 때만 넣는다.
- 문장 수를 고정하지 않는다. 논점이 바뀌면 문단을 나누고 긴 줄글이 이어지지 않도록 적절한 소제목·그림·표를 사용한다.
- 별도의 요약·결론·맺음말을 만들지 않는다. 필요한 설명이 끝나면 글을 끝낸다. 출처가 있다면 참고문헌 목록은 둘 수 있다.

## 시각 표현

- 단정하고 화면에서 읽기 좋은 고딕 계열 글꼴을 사용한다. 한글·영문·숫자의 조화를 고려한다.
- 네이비·블루 계열로 차분하고 학술적인 분위기를 만든다. 용도 불명의 핑크색 강조를 사용하지 않는다.
- 정의·예시·주의사항은 별도로 짚어야 할 내용에 한해 박스로 구분한다. 옅은 배경색, 절제된 테두리와 역할을 나타내는 제목을 사용한다. 색상만으로 의미를 전달하거나 일반 문단까지 모두 박스로 만들지 않는다.
- 문단 사이와 소제목·그림·표 앞뒤에 넉넉한 여백을 둔다. 화면에서 실제 간격과 정보 밀도를 확인한다.
- 원리는 흐름도·구조도 등 도식으로, 적용과 결과는 실제 자료·스크린샷·데이터 그래프로 설명한다. 실제 자료가 없으면 결과를 지어내지 말고 자료 부족 절차를 따른다.
- 이미지의 가로세로 비율을 유지하고 본문·화면 너비를 넘지 않게 한다. 축소 후에도 레이블을 읽을 수 있어야 한다. 복잡한 이미지는 필요한 경우 확대해서 볼 수 있게 한다.
- 간단한 자료는 화면에 맞추고, 복잡한 표·코드·수식은 필요할 때 해당 영역 안에서만 가로 스크롤하게 한다. 페이지 전체에 가로 넘침이 생기지 않도록 한다.

## 출처

- 논문은 본문에서 `[1]`, `[2]`처럼 번호로 인용하고 글 아래 참고문헌에 대응시키며 원문 링크를 제공한다.
- 공식 문서와 코드는 관련 설명에 직접 링크한다.
- 실제로 확인한 자료만 인용한다. 참고문헌을 위해 별도의 마무리 문단을 만들지 않는다.

## 저장소 적용과 로컬 검토

- 저장소 루트의 `AGENTS.md`를 먼저 읽고, 필요한 경우 해당 영역의 지침을 확인한다. 글은 `_posts/`의 기존 메타데이터·날짜·경로 규칙을 따른다.
- 기존 글은 기술적인 연동 방식의 참고 자료로만 사용한다. 기존 말투·핑크색·밀집된 여백을 선호 스타일로 복제하지 않는다.
- 목차, 수식, 이미지 확대 등은 현재 설치된 테마·플러그인의 지원 방식과 설정을 확인한 뒤 사용한다. 프런트매터 옵션을 추측해서 추가하지 않는다. 목차는 데스크톱 사이드바에만 의존하지 않고 모바일에서도 글 상단에서 접근할 수 있게 한다.
- 스타일 변경은 대상 글에 한정되도록 범위를 설정한다. 사이트 공통 스타일 수정이 필요하면 영향 범위를 설명하고 사용자와 조율한다. 저장소의 런타임·레이아웃 소유권 규칙을 따른다.
- 미리보기 주소와 빌드 설정은 현재 `_config.yml`과 실행 환경에서 확인한다. 이 사이트는 확인 당시 `url: https://redstonecold.github.io`, `baseurl: ""`였다. 상위 템플릿 문서의 `/al-folio` 경로를 무조건 적용하지 않는다.
- 전체 초안 작성 후 실제 로컬 블로그 화면으로 검토한다. 대표 구간과 모바일 화면에서 글꼴, 여백, 제목·목차, 박스, 그림·표 배치와 넘침을 확인한다. 대표 구간에는 사용된 주요 표현 유형과 가장 넓거나 복잡한 자료를 포함한다.
- 목차 링크, 사용한 수식·코드 렌더링, 이미지 크기 등 변경에 관련된 검증을 수행한다. 같은 화면을 반복해서 캡처하거나 전체 페이지를 불필요하게 재검사하지 않는다. 수정 후에는 바뀐 부분과 직접 영향을 받는 영역만 재확인한다.
- 사용자에게 로컬 미리보기를 열어 실제 화면으로 검토하게 한다. 미리보기를 실행할 수 없으면 장애와 확인하지 못한 범위를 알리고 다음 진행 방법을 질문한다. 화면을 보지 않고 시각 검증을 완료했다고 말하지 않는다.
- 전달할 때 미리보기 접근 방법과 검토에 필요한 사항을 간결하게 안내하고 사용자 피드백을 기다린다.
